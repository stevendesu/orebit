Optimization ideas:
===================

**Idea 1: Futility Flood**

We can "detect" flooding if we just popped an expensive node then popped a cheap node far away. Basically if h() > bestH then we're about to consider a potential flood.
There must be some way to do a cheaper "proof of futility" without running full-A*. Considered flood fill or other options here...

**Idea 2: Greedy-like non-admissible heuristic adjustments**

At the block level, perhaps a quadratic distance term when you're outside of the skeleton to discourage looking in the wrong direction?

At the block level, perhaps a guard at sea level (if the goal is Y > 63, punish exploring Y < 62) to avoid pathological floods into the ocean?

**Idea 3: Scatter safe-fall**

During NavGrid build the same way we now scatter for "risky edit", we can scatter safe fall distances. If there's water, set a "safe fall" bit on every block above it.
This would eliminate the downward scan during searches and replace it with checking a single "can I drop here" bit.
Could also revive the idea of "a run of 2 climbables interrupts a fall from N height, a run of 3 interrupts from M height".

Idea 3 was investigated and rejected as-written, but Claude had a few ideas based on this which might be worth considering. Some notes:
 * There is no free bit in the NavGrid short. 10 bits are used for the navtype descriptor index and the other 6 are all accounted for. We can't afford a "safe fall" bit
 * Even if we COULD afford a "safe fall" bit -- scattering to the ~6 neighbors isn't the same as scattering to an unbounded column above. This would make NavGrid construction outrageously slow
 * 99% of the time we aren't even reading the depth nibble (4 neighboring cells are same Y level or a 1-level difference: not a fall)
 * The 1% of the time that we ARE reading the depth nibble, 99% of THOSE the landing block is within 14 so the depth nibble works
 * The 1% of the time we go beyond the depth nibble, we can still jump 14 at a time so the total number of reads is low(-ish)

Still, Claude said there may be some recoverable ideas here, so leaving this on the table

**Idea 4: Pre-fetch neighbors**

I believe Ascend, Traverse, and Descend all independently read the 4 cardinal cells (to determine if they're solid, passable, etc).
We could pull these once outside of ANY specific movement's logic and pass them as inputs to all movements.
So movements get a pointer to the NavGrid plus a handful of pre-pulled cells that we know they're likely to need.

IN GENERAL: I'd love to do another JFR run and understand where we're spending our time. We've accepted multiple "+3%" costs to add new features, and those compound.

**Idea 5: Grow our NavGrid values from 16-bit to 32-bit**

The goal of things like our headrooms bits and risky_edits bits was, allegedly, to pre-compute anything that depends on neighbor cells.
This way when doing our hottest path reads we can look at a single cell and know everything we need to know in order to compute valid movements.

The issue is that 6 bits of flags wasn't nearly enough to store EVERYTHING we needed. Headroom is nice and all, but we still end up reading MULITPLE
neighbor cells to answer questions like "is the neighbor in the +x direction climbable" or "is the landing cell for the parkour slippery"

Increasing the size of our values means doubling our RAM usage, which also means slower reads since our NavGrid will spread over more cache lines.
However it also means we can store more pre-computed values, which may mean fewer nodes being read **at all**

TWO major concerns:

 1. We need an inventory of every single time we read a neighbor cell and what we're reading from it
 2. We need to consider how world edits impact that. When a cell is edited, that edit could scatter to neighbors now

**IDEA 6 -- NEWEST AND BIGGERIST IDEA**

Okay, so in the past we tried using flood fill as a cheap "test of futility" when we started to flood. Instead of running A* in an ocean, we
said "quickly scan the ocean to see if it's even possible to reach a better position from here"

The problem was that it added MASSIVE complexity and the flood fill was only about 3x faster than A*

So for 99% of searches we don't flood (never triggered) and for the 1% that flood we still had a millisecond budget (either explicitly for async
or implicitly to stay within a 50ms tick for sync) so it's not like we could suddenly flood MASSIVE plains... We went from a 10k node budget to
a 30k node budget AT BEST (but only the futility check was faster, not the A*, so it was more realistically like 20-25k)

But we just recently fixed flooding at the REGION tier with a clever trick. I realized that there was no reason to scan unbuilt regions AWAY from
the goal into an endless void - because provably any path through that unbuilt sea could be trimmed due to the guaranteed six-connectivity of our
optimistic unbuilt regions. It trims to exactly the shell wrapping our built regions. A path through unbuilt space never needs to do more than:
 * Dip out of the unbuilt regions
 * Surf around the shell
 * Dip back in at a built location where we could cheaply reach the goal

So we built this. There were some caveats like "we can extend more than 1 region into unbuilt space if doing so reduced h" - this allows us to
bridge across an unbuilt void. Or we allow a single expansion into the unbuilt void in order to route around corners.

After building this we had an issue: one of our test fixtures was intended to cause region flooded at the L0 level by forcing a path around a
huge unbreakable wall when there was a huge region of unbuilt space behind us. The search would flood that unbuilt space looking for a way around
the wall that didn't exist. The test then checked that when this flooding occurred, we escalated to the L1 region tier.

The issue was that the new, smarter rules for unbuilt regions meant we never flooded anymore. We knew to never scan the regions behind us (they
provably CAN'T contain a faster route to the goal) and we cheaply hugged the wall at the L0 tier as we scanned around it and found the path.

I realized that this same clever "scan the shell" technique could work at the block tier! If we're starting to flood, then instead of running
flood fill we could limit A* to only checking nodes along the "shell". So if a move increases h (we're moving away from the goal), only pop it
if the block is adjacent to a non-passable cell. Or something like that. This way we can cheaply flood the PERIMETER and find another way in
without wandering into the ocean.

I don't have it 100% fleshed out in my head, but I'm like 95% sure this will work!
