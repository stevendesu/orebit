Optimization ideas:
===================

**Idea 1: Futility Flood**

We can "detect" flooding if we just popped an expensive node then popped a cheap node far away. Basically if h() > bestH then we're about to consider a potential flood.
There must be some way to do a cheaper "proof of futility" without running full-A*. Considered flood fill or other options here...

**Idea 2: Greedy-like non-admissible heuristic adjustments**

At the block level, perhaps a quadratic distance term when you're outside of the skeleton to discourage looking in the wrong direction?

At the block level, perhaps a guard at sea level (if the goal is Y > 63, punish exploring Y < 62) to avoid pathological floods into the ocean?

**Idea 3: Scatter safe-fall**

During NavGrid build the same way we now scatter for "risky edit", we can scatter safe fall distances. If there's water, set a "safe fall" bit on every block above it.
This would eliminate the downward scan during searches and replace it with checking a single "can I drop here" bit.
Could also revive the idea of "a run of 2 climbables interrupts a fall from N height, a run of 3 interrupts from M height".

Idea 3 was investigated and rejected as-written, but Claude had a few ideas based on this which might be worth considering. Some notes:
 * There is no free bit in the NavGrid short. 10 bits are used for the navtype descriptor index and the other 6 are all accounted for. We can't afford a "safe fall" bit
 * Even if we COULD afford a "safe fall" bit -- scattering to the ~6 neighbors isn't the same as scattering to an unbounded column above. This would make NavGrid construction outrageously slow
 * 99% of the time we aren't even reading the depth nibble (4 neighboring cells are same Y level or a 1-level difference: not a fall)
 * The 1% of the time that we ARE reading the depth nibble, 99% of THOSE the landing block is within 14 so the depth nibble works
 * The 1% of the time we go beyond the depth nibble, we can still jump 14 at a time so the total number of reads is low(-ish)

Still, Claude said there may be some recoverable ideas here, so leaving this on the table

**Idea 4: Pre-fetch neighbors**

I believe Ascend, Traverse, and Descend all independently read the 4 cardinal cells (to determine if they're solid, passable, etc).
We could pull these once outside of ANY specific movement's logic and pass them as inputs to all movements.
So movements get a pointer to the NavGrid plus a handful of pre-pulled cells that we know they're likely to need.
